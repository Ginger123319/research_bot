01 · PROBLEM

手工评估的三道墙

每接一个新模型，之前的经验几乎无法复用——因为它从未被显式地记录下来

01 ⏱
耗时长，全程手动
部署 → 探针 → 数据处理 → 压测 → 分析 → 报告，每个环节都需要手动切换脚本、核对参数、确认输出。
每模型完整评估 2~3 天
02 🔁
脚本分散，经验无法沉淀
每个模型的压测脚本各自定制，参数命名不统一，遇到类似问题需要重新摸索，跨模型重复劳动约 60%。
15+ 次手工介入 / 模型
03 🔍
过程不可见，根因难定位
压测在远端 GPU 服务器运行，本地不可见；avg_output_len 高估、并发污染等问题发现严重滞后，排查成本高。
每次根因排查 4h+
↓  把经验变成资产

// ACCUMULATED INSIGHTS · 3 个跨模型技术发现沉淀至 Skill 规则
  • 超长 Prompt（>4K）场景 DP 配置失效，安全拦截模型必须使用 TP 并行（tianji-4b 验证 → llm-deployment-docker Skill 规则更新）
  • TP8/TP4 承载倍数 ≈ 1.6× 而非理论 2×，TP 通信开销不可忽略（ziwei-32b 验证 → qps-sweep-comparison SLA 评估更新）
  • 72B 长输出模型 TTFS P90 SLA 建议放宽至 ≤ 1.6s，严格 1.5s 对此类模型偏紧（hepan 验证 → model-eval-report 报告模板更新）
05 · SCALE

从个人工具到团队基础设施

Skill 体系的价值不在于某次评估做得更快——而在于它可以被任何人使用、持续强化

→
横向：任意新模型快速接入

新模型不再需要从零开始搭建评估流程，直接复用 workflow + Skill 体系

  • ✓ 部署：llm-deployment-docker Skill 一键完成预检 + 启动 + 健康检查
  • ✓ 数据：traffic-dataset-prep 5步标准化管道
  • ✓ 测试：qps-peak-finder 三阶段，~10~15档即可收敛边界（替代原来 40+档）
  • ✓ 报告：model-eval-report 自动生成交付文档，含资源推荐

↑
纵向：Skill 持续强化迭代

每次评估发现的新边界条件和踩坑，直接反哺对应 Skill 的规则和检查清单
