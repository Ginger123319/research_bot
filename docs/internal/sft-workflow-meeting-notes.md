## **4. 资源 & 规模约束**

- **当前主要模型规模**（72B / 122B / 235B｜Dense or MoE）：均跑在 ms-swift 上；后端按规模切换——小于 14B 走 DeepSpeed，其他走 Megatron
- **未来训练计划**：122B 和 235B 是主流；后续还有 kimi-k2.5 / k2.6 的训练，规模大概率只增不减
- **GPU 现状**：8 台 H200、每台 8 卡，集群总规模 **64 卡**；以多机分布式训练为主
- **单次 SFT 典型时长**：lingyu 级别的模型，使用 8 台机器一起训练通常十几个小时
- **最难受的束缚**：人力手工活较多；资源使用需要排队、串行使用（单次训练任务独占全部 8 台 / 64 卡）

## **5. 微调方法现状**


| **方法**                    | **使用占比** | **选用理由（精度 / 显存 / 速度）**     | **痛点**              |
| ------------------------- | -------- | -------------------------- | ------------------- |
| 全参 SFT                    | 较大       | 资源够用时优先全参，避免精度损失           | —                   |
| LoRA                      | 很小       | 仅在模型规模过大、全参跑不动时退化使用        | —                   |
| QLoRA                     | 无        | LoRA 场景下显存已够用， 没必要再上 QLoRA | —                   |
| 其他（DPO / GRPO / RLHF ...） | 较大       | 走 ms-swift（GRPO）或 verl 框架  | 需手动设计奖励函数， 不同模型会有差别 |

## **6. 评估 / checkpoint 现状**

- **评估流程是否 in-the-loop**：训练内嵌自定义测试集评估（in-the-loop）；评估组的最终评估在训练完成后做（offline）
- **checkpoint 大小 / 产出频率**：保留最近 3–5 个，或测试集上效果最好的那一个
- **管理与复用**：统一路径存放，需要使用时再加载

---

## **7. 关键判断**

- **算法部门当前最大束缚**：人力手工活较多 + 训练监控没法动态观测 + 断点续训在分布式训练时不稳定
- **二开整体方向**：集成或改造 Megatron 中的并行训练技术，参考 ms-swift 的参数配置方式，增加框架的易用性和扩展性
- **QLoRA 优先级**：备选，优先级不高
  - 依据：§5 LoRA 占比很小、QLoRA 无；Pain #4 的 "int4 全参 SFT" 属 QAT 范畴，不是 QLoRA 的解决域
- **偏好学习 / RL（DPO / GRPO / RLHF）是否纳入新框架范围**：**待定**
  - §5 占比"较大"，但当前由 ms-swift / verl 自行承接；纳入与否会显著影响二开工作量
- **工具栈集成方向**：新框架只负责训练的核心部分（参数推荐 / 监控 / 断点续训 / 冻结训练等），数据沿用 ai-data 那一套现有的处理逻辑、评估对接评估组、checkpoint 走统一路径约定，不做端到端平台
  - **初步判断**，后期还需要收集更多信息来综合分析
- **Top 3 优先优化点**（排序依据：频率 × 严重度，且必须在训练框架解决域内）：
  1. 训练参数自动化配置 / 推荐（对应 Pain #7，频繁 × 严重）
  2. 训练监控实时可视化（对应 Pain #2，很高 × 中等）
  3. 提升断点续训在分布式训练中的稳定性（对应 Pain #1，偶尔 × 严重）
  > 未进入 Top 3 的 Pain #4（int4 训练，中等 × 严重）按频率劣后；如后续 int4 基座占比上升，可重排
