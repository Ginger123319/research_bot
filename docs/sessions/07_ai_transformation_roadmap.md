# AI 化成长路线图

**日期**：2026-05-08  
**背景**：从只用 Cursor 编程出发，系统规划个人 AI 化路径  

---

## 一、AI 化成功的特征

| 特征 | 说明 |
|------|------|
| **人在 AI 旁** | AI 在做事、人在监督，而非人在做事、AI 辅助 |
| **正交自动协作** | 各模块互不耦合、可并行，而非 A 完成才能 B 开始的串联流程 |
| **模型涌现** | 系统行为从模型能力中自然涌现，而非被硬编码的固定规则 |
| **高效率、自进化、强适应** | 结果侧指标，前三条做到后自然成立 |
| **失败可观测**（补充） | 自进化的前提是能感知哪里做错了，需要 tracing/logging/evaluation |

---

## 二、任务优先级排序

### 第一梯队：本周就做，立竿见影

**① 沉淀 Skill / Rule**（最高优先）
- 难度：⭐
- 收益：每写一条，后续所有对话都受益，复利效应最强
- 做法：每次发现 AI 给的答案不好，花 5 分钟把正确做法写进 `.cursor/skills/` 或 `.cursor/rules/`

**② research_bot 覆盖日常文档场景**
- 难度：⭐⭐
- 收益：把调研/写报告的时间压缩 60%+
- 做法：工作中遇到要查资料、写总结的任务，强迫自己先走 research_bot，不要直接自己查

**③ 建立 AI 效果周记**
- 难度：⭐
- 收益："自进化"的唯一入口，没有记录就没有进化
- 做法：在 `docs/todolist/` 里维护周记，记"AI 节省了哪些时间、哪里还不好用"

---

### 第二梯队：本月做，建立链路

**④ 代码 Review 自动化**
- 难度：⭐⭐⭐
- 收益：提 PR 后 AI 先过一遍，减少低级问题流到人工 review
- 做法：先试 Cursor BugBot（设置里直接开），再考虑 GitHub Actions

**⑤ 异常日志 AI 分析节点**
- 难度：⭐⭐⭐
- 收益：测试失败/日志报错时 AI 自动给出原因，不用人肉翻日志
- 做法：写脚本把错误日志 pipe 给 AI，输出分析结果

---

### 第三梯队：3 个月内，跑通完整 Agent 链路

**⑥ 端到端 Agent 工作流**
- 难度：⭐⭐⭐⭐
- 收益：真正体验"正交自动协作"，认知跃迁
- 做法：先用 Cursor Agent 把一个完整任务（需求→代码→测试→部署）跑通，遇到"必须人在场才能继续"的节点，再引入 LangGraph/AutoGen

**⑦ 可观测指标体系**
- 难度：⭐⭐⭐⭐
- 收益：支撑长期自进化
- 做法：等⑥跑通后设计 metric，不要提前过度设计

---

### 执行路径总览

```
本周
  ├── ① 沉淀 Skill/Rule        ← 今天就能开始
  ├── ② research_bot 扩用途    ← 改习惯，零技术成本

本月
  ├── ④ 代码 Review 自动化

3 个月内
  ├── ⑥ 端到端 Agent 工作流
  └── ⑦ 可观测指标体系
```

## 三、关于 Cursor 与专业 Agent 框架的边界

Cursor Agent 能覆盖约 70% 的 Agent 需求，剩余 30% 需要专业框架：

| 能力 | Cursor | 专业框架（LangGraph/AutoGen） |
|------|--------|-------------------------------|
| 多步骤自主执行 | ✅ | ✅ |
| MCP 接入外部工具 | ✅ | ✅ |
| 多 Agent 并行协作 | ❌ | ✅ |
| 定时自动触发（无人值守） | ❌ | ✅ |
| Agent 间状态传递 | ❌ | ✅ |
| 长期跨会话记忆 | ❌ | ✅ |
| 生产级错误重试/监控 | ❌ | ✅ |

**建议**：先用 Cursor 把 70% 跑透，遇到明确瓶颈再升级，目标明确学起来也快。

## 四、学习效果评估体系

### 能力维度——能不能独立完成

| 阶段 | 检验问题 | 通过标准 |
|------|----------|----------|
| 第一梯队 | 遇到新问题，能否 5 分钟内写出有效 Skill/Rule？ | 写完后 AI 真的不再犯同样的错 |
| 第一梯队 | 拿到调研任务，全程用 AI 完成，质量达标吗？ | 不需要大量人工补充，直接可用 |
| 第二梯队 | Review 自动化跑起来后，能发现多少之前漏掉的问题？ | 每次 PR 至少 1 条有价值的 AI 意见 |
| 第三梯队 | 能否让 Agent 工作流全程自己跑完？ | 你只 review，不手动介入 |

### 习惯维度——自然而然用 AI

一个月后问自己：
1. 遇到不会的问题，第一反应是问 AI 还是自己搜？
2. 重复性的事情，会不会主动想"能不能让 AI 自动化"？
3. AI 给了不好的答案，会不能沉淀成 Skill，还是算了下次再说？

三个都是"会"，习惯建立了。

### 量化指标

每周记录一个数字：

```
AI 替代率 = 本周 AI 完成的工作量 / 总工作量
```

粗估即可。第一周约 20%，三个月后目标 60%+。

### 三个月终检标准

- [ ] 有没有一件以前要半天的事，现在 AI 帮你 30 分钟搞定？
- [ ] 有没有一个流程，现在是 AI 在跑、你在看结果？
- [ ] Skill 库有没有超过 10 条你真正在用的规则？

三个"是"，说明真正做成了。

## 五、AI 替代不了的积累

### 判断力：不需要比 AI 厉害，但需要能识别问题

- **比 AI 厉害**：你能写出比它更好的答案
- **有判断力**：你能识别它的答案哪里有问题

判断力的核心不是专业知识，而是：目标清晰 + 经验积累的直觉 + 知道怎么验证。

**AI 容易出错的地方，需要保持警觉：**

| AI 容易出错的地方 | 应对方式 |
|------------------|----------|
| 细节看起来对但逻辑有漏洞 | 追问"为什么"的习惯 |
| 给出听起来自信但实际过时的信息 | 问"这是最新的吗" |
| 迎合预期给出你想听的答案 | 主动问"有没有反对意见" |
| 把复杂问题过度简化 | 问"有哪些我没考虑到的情况" |
| 代码能跑但不符合实际约束 | 给足约束条件，而不只是描述功能 |

> 你不需要比 AI 厉害，但你需要比 AI 更了解你自己的问题。

---

### 工作中要刻意积累的

**① 每个线上问题，先自己推断根因再看答案**

场景：GPU 节点掉了，告警来了。
- 普通做法：日志扔给 AI，照着修
- 要刻意做的：先自己看 10 分钟，形成假设，再去验证
- 为什么：一年 50 个这样的经历，你对这个集群特定规律的感知是 AI 没有的

**② 方案落地时，记录"为什么没选另一个"**

场景：选了方案 A，没选 B。
- 要刻意做的：写一句话——"B 方案在我们的网络拓扑下延迟会高，所以没选"
- 为什么：半年后能清楚说出每个技术选型背后的约束，而不是"当时就这么做的"

**③ 跟业务方对话，主动问"为什么要这个"**

场景：业务方说"我要把推理延迟压到 50ms"。
- 要刻意做的：问"为什么是 50ms？100ms 会有什么影响？"
- 为什么：很多需求背后的真实约束跟表面说的不一样，AI 永远不会主动帮你问这个

**④ 观察做决策好的人，拆解他们怎么想**

场景：leader 在评审会上否掉了一个方案。
- 要刻意做的：会后问"你当时主要是担心哪个点"，复盘他的逻辑链
- 为什么：判断力是可以"抄"的，观察足够多好的决策会内化出自己的标准

---

### 工作之余该补什么

**① 读真实系统的设计文档，不是教程**

推荐：Google/Meta/字节技术博客、Kubernetes/Ray 的 GitHub issue、真实系统的事故复盘
不推荐：入门教程、没有上线经历的技术文章
怎么读：不只是"知道了"，问自己"如果是我们的场景，这个方案哪里会有问题"

**② 把 research_bot 做深，而不是做新项目**

一个真实跑着的项目（有人用、要维护、有边界情况）教你的东西，比看 10 篇文章多。
加监控、加评估、处理真实的异常——这些是教程里没有的。

**③ 找一个比你强的人定期对话**

不是找人教你，是找能聊技术判断的人——"你觉得这个方案怎么样"、"你选型时最看重什么"。
把自己模糊的感觉说清楚，说清楚的过程就是思维成型的过程。

**④ 定期看自己六个月前写的方案/代码**

翻出半年前的设计文档，评价它——"现在我会怎么做得不一样"。
这是感知自己成长最直接的方式，也会发现自己反复犯的同一类错误。

### AI 替代不了的积累总结

```
AI 替代的是：信息处理、方案生成、重复执行
你需要积累的是：经历、对人的理解、品味、独特视角、承受不确定性的能力

AI 让"知道"变得廉价
所以"经历过"和"真正理解"的价值反而升高了
```

## 七、AI 时代三个流行论断的批判性分析

> 来源：2026-05-08 讨论。记录在这里是为了训练判断力——对看起来正确的说法，分析它对在哪、错在哪。

---

### 论断一：Harness 为 AI 搭建了软件开发新范式

**说的是：** 软件开发核心从"人写代码"转向"人定义约束和意图，AI 生成实现"，整个工程体系围绕新分工重建。

**说得对的地方：**
- 描述了真实发生的趋势：工程师角色确实在向"验证者"和"架构者"偏移
- 指出了系统性重建的方向：不只是工具升级，测试、CI/CD、代码审查都需要重新设计
- 不是单点工具论，而是全生命周期视角

**说得有问题的地方：**
- 落地条件被低估：大多数团队测试覆盖率、可观测性远没准备好，离"AI 主导生成、人验收"差很远
- 对遗留系统没有答案：存量几十万行老代码的业务，这个范式很难落地
- "范式"二字有营销成分：Harness 是 CI/CD 平台，需要区分真实洞察和产品叙事

---

### 论断二：AI 时代人需要具备主动性、判断力、架构能力、领导力

**说的是：** 这四种能力是 AI 替代不了的人的核心价值。

**说得对的地方：**
- 判断力和架构能力确实是 AI 短板：跨系统权衡、长期演化设计仍需要人
- 主动性是真实的稀缺："发现值得做什么"这件事 AI 做不了
- 方向正确，这四个能力确实难被替代

**说得有问题的地方：**
- 门槛被模糊：架构能力需要大量真实系统经验，说法容易让人以为转型很简单
- 执行能力仍然重要：完全不写代码的"架构师"会越来越脱节，AI 生成的代码你要能看懂、能验证
- "领导力"太泛：是带人？影响决策？还是驱动 AI Agent 完成任务？不同理解差很远
- 有幸存者偏差风险：这四种能力的人本来就稀缺，正确但缺乏操作性

---

### 论断三：Rust 和 TypeScript 是 AI 友好的语言

**说的是：** 这两种语言的强类型系统让 AI 生成的代码质量更高、更可验证。

**说得对的地方：**

TypeScript：
- 类型系统给 AI 提供了强约束，编译器直接过滤类型错误，降低人工审查负担
- 类型即文档，AI 理解接口契约比理解自然语言注释更准确

Rust：
- 所有权系统强迫 AI 写出内存安全的代码，否则编译不过——是最强的输出质量过滤器
- 错误必须显式处理（`Result<T, E>`），AI 不能偷懒跳过错误处理
- 编译器报错详细，AI 能根据报错自我修正

**说得有问题的地方：**
- Rust 对 AI 也更难：所有权、生命周期是双刃剑，AI 写 Rust 的一次正确率明显低于 Python/Go，需要更多轮迭代
- TypeScript 容易被绕过：`any`、类型断言、不严格的 tsconfig 都能让类型系统形同虚设
- "AI 友好"不等于"团队友好"：Rust 学习曲线陡，团队没有基础时 AI 生成的代码无法被有效审查，反而更危险
- 忽视了 Python：AI/ML 领域 Python 是主导，AI 对 Python 的生成质量可能最高（训练数据最多）

---

### 三个论断的共同规律

| 论断 | 核心洞察 | 主要问题 |
|------|----------|----------|
| Harness 新范式 | 方向正确，范式转变是真实的 | 落地条件被低估，有营销包装 |
| 人的四种能力 | 能力方向正确 | 门槛模糊，执行能力仍不能丢 |
| Rust/TS AI 友好 | 强类型确实降低审查负担 | Rust 生成难，TS 易被绕过，Python 被忽视 |

**规律**：这三个说法都抓住了真实趋势，但都存在过度简化或忽视反例的问题。这是 AI 时代内容的典型特征——**方向对，细节经不起推敲**。

识别这个模式本身就是判断力的一部分。
