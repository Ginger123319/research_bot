## 4. 拐点分析

### 核心结论：拐点在 QPS ≈ 8.0~8.5 req/s

| 阶段 | QPS 区间 | E2E P90 | E2E P95 | 描述 |
|------|---------|---------|---------|------|
| **低负载稳定区** | 4.0 ~ 5.5 | 0.2s | ≪0.4s | 延迟极低，全命中缓存为主 |
| **中负载平稳区** | 5.5 ~ 7.0 | 0.2~0.3s | ≤0.4s | 小幅抬升，仍有余量 |
| **缓存热身异常点** | 6.90 ~ 7.00 | 0.1~0.2s | ≤0.4s | KV Cache 充分预热，延迟骤降（详见 §4.1） |
| **过渡区** | 7.0 ~ 8.0 | 0.1~0.3s | ≤0.4s | 延迟回升但仍满足 SLA |
| **拐点** | **8.0 → 8.5** | 0.3 → 0.4s | **0.40 → 0.422s** | **E2E P95 首次突破 400ms** |
| **过载区** | 8.5 ~ 10.0 | 0.4~0.5s | 0.422~0.530s | 延迟持续抬升，P95 越界越深 |

### 4.1 KV Cache 热身效应（QPS=6.90 / 7.00 延迟骤降）

在 QPS=6.90 时 TTFS P90 从 0.283s 降至 0.236s，QPS=7.00 时进一步降至 0.138s（全程最低），这是 SGLang 前缀缓存的预热效应：

- 相同 8K system prompt 的请求在单位时间内越密集，KV Cache 命中率越高
- QPS=7.0 时缓存充分"热身"，几乎所有请求完全跳过 prefill，延迟骤降
- QPS=7.5 时由于新增并发压力，部分请求等待时间上升，延迟回升至 0.294s
- 此现象**非性能退化**，是 SGLang 前缀缓存机制的正常体现

### 4.2 拐点触发机制

从 QPS=8.0 → 8.5，E2E P95 从 ≤0.40s 升至 0.422s（超标 5.5%），触发机制分析：

- QPS ≥ 8.5 时，服务并发度接近饱和，后续请求等待前序请求释放 GPU 资源
- 尽管每条请求的 TTFS/E2E P90 仍在 0.4s 以内，但 P95 尾部延迟（队列等待 + 计算时间）开始超标
- 成功率全程 100%，说明服务**未过载崩溃**，仅处于"轻度尾延迟超标"状态
- QPS=9.5~10.0 时 E2E P90 本身也超标（0.4~0.5s），进入明显过载区

## 5. 结论与建议

### 5.1 核心结论

| 维度 | 结论 |
|------|------|
| **SLA 合规最大 QPS** | **8.0 req/s（480 RPM）** |
| 当前业务峰值 | 约 36.1 req/s（2168 RPM） |
| 当前部署容量 | 仅满足 480 RPM，覆盖业务峰值的 **22%** |
| 拐点位置 | QPS = 8.0~8.5，由 E2E P95 触发 |
| 主要瓶颈 | GPU 并发计算饱和（非缓存、非网络） |

### 5.2 扩容建议

要覆盖业务峰值 2168 RPM（≈36.1 req/s），所需 4TP 实例数：

```
N = ceil(36.1 / 8.0) = ceil(4.5125) = 5 个 4TP 实例
总 GPU 需求 = 5 × 4 = 20 卡 H100
```

若保留 20% 安全余量（实际限流上限 6.4 req/s/实例）：

```
N = ceil(36.1 / 6.4) = ceil(5.64) = 6 个 4TP 实例
总 GPU 需求 = 6 × 4 = 24 卡 H100
```

### 5.3 与 4DP 方案对比

| 对比维度 | 4TP×1实例 | 1TP×4DP |
|---------|---------|---------|
| SLA 合规最大 QPS（单部署单元）| **8.0 req/s** | **None（全部不达标）** |
| E2E P90（典型值）| 0.2~0.3s | 1.5~2.5s |
| 覆盖业务峰值所需 GPU | 20~24 卡 | 无法满足 |
| **推荐结论** | **✅ 采用** | **❌ 不可用** |
