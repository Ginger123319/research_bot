## 1. 测试背景

### 对比目的

相同 GPU 总量（4 卡 H100）下，比较两种部署策略：

| 部署方式 | 描述 | GPU 使用方式 |
|---------|------|-------------|
| **4TP×1实例** | 4 GPU 张量并行，单实例 | 4 GPU 协同处理每条请求 |
| **1TP×4DP** | 1 GPU 单实例 × 4 副本（数据并行）| 每条请求由 1 GPU 独立处理 |

两组测试均使用相同数据集、相同 QPS 范围（4.0 → 7.0，30 档，每档 45min）。

### 模型特征

| 项目 | 值 |
|------|----|
| 模型 | `tianji_query_safety/v2p3_ep1`（4B 安全检测） |
| System Prompt | ~8K Token（固定大模板 + 大量 few-shot） |
| User Input | 极短（几十 Token） |
| 最大输出 | 256 Token（短 JSON 结构化输出） |
| 部署框架 | SGLang（开启 KV Cache 前缀匹配） |

### SLA 基准（模型特定）

| 指标 | 门限 | 说明 |
|------|------|------|
| **E2E P95** | **≤ 400ms** | 主判断指标（快进快出结构） |
| TTFS P90 | ≤ 1,500ms | 首句延迟通用基准 |
| E2E P90 | ≤ 400ms | 辅助判断 |
| 请求成功率 | ≥ 99% | 稳定性基准 |

## 4. 深度分析

### 4.1 两组性能差距的根本原因：张量并行 vs 数据并行对 Long-Prefix Prefill 的影响

| 对比维度 | 4TP×1实例 | 1TP×4DP |
|---------|---------|---------|
| 每条请求处理 GPU 数 | **4 GPU 协同** | **1 GPU 独立** |
| 8K system prompt prefill 时间 | ~0.1~0.2s（4 GPU 并行分摊） | ~1.5~2.5s（单 GPU 串行全量） |
| KV Cache 共享范围 | 单实例内所有请求共享前缀缓存 | 每个副本独立缓存，缓存命中率低 |
| 服务延迟量级 | 0.1~0.3s（满足 SLA） | 1.5~3.5s（超出 SLA 4~10 倍） |

**核心机制**：该模型 system prompt 为 8,192 Token，每条请求进入服务时都需要先对这 8K Token 执行 prefill（注意力计算）。  
- 4TP 模式下，4 块 GPU 并行分摊注意力头（attention head splitting），每块 GPU 仅需处理 1/4 的计算量，prefill 速度接近线性加速（约 4x 提升）。  
- 1TP 模式下，单块 GPU 必须独立完成整个 8K token 的注意力计算，计算时间 ≈ 4TP 的 4 倍。  

### 4.2 4TP 特殊现象：高 QPS 时延迟反而下降（"缓存热身效应"）

| QPS 档位 | TTFS P90 | E2E P90 | 趋势说明 |
|---------|----------|---------|---------|
| 6.59 | 0.289s | 0.3s | 阶段高点 |
| 6.69 | 0.283s | 0.3s | 微降 |
| 6.79 | 0.280s | 0.3s | 微降 |
| 6.90 | 0.236s | 0.2s | **明显下降** |
| **7.00** | **0.138s** | **0.1s** | **全程最低** |

**解释（SGLang KV Cache 前缀缓存预热）**：
- SGLang 对相同前缀的 KV 状态进行缓存，匹配到缓存时完全跳过 prefill 计算
- QPS 越高 → 单位时间内同前缀请求越密集 → 8K token system prompt 的 KV 缓存命中率越接近 100%
- QPS=7.0 时缓存已充分"热身"，几乎所有请求直接跳过 prefill，延迟大幅下降至 0.1s
- 这是 SGLang 前缀缓存机制的直接体现，**非性能退化，而是加速效果**

### 4.3 4DP 是否出现相同的"高 QPS 延迟下降"现象？

**结论：没有。**

分析 1TP×4DP 的延迟曲线：
- E2E P90 在 1.5s ~ 2.5s 之间**随机波动**，无任何下降趋势
- TTFS P90 同样无规律，甚至在高 QPS 时（QPS=5.66: 2.511s）出现更大值

原因分析：
1. **每个 DP 副本实际接收 QPS ≈ 总 QPS / 4 = 1~1.75 req/s**，单副本流量较低，前缀缓存不易充分预热
2. **单 GPU 的 prefill 瓶颈**决定了每条请求基本都需要重新计算（或冷缓存命中），缓存收益无法抵消计算开销
3. 即使在全缓存命中的理想情况下，单 GPU 处理 8K token 的 decode 阶段延迟也约为 0.5s+，仍无法满足 400ms SLA

### 4.4 延迟量级比较

| 延迟指标 | 4TP×1实例（最差） | 1TP×4DP（典型） | SLA 门限 | 倍差 |
|---------|----------------|----------------|---------|------|
| E2E P90 最大值 | 0.3s | 2.5s | 0.4s | **8.3x** |

## 5. 结论与建议

### 5.1 核心结论

| 维度 | 结论 |
|------|------|
| **整体判断** | **4TP 完胜 4DP，4DP 方案不可用于生产** |
| 4TP SLA 合规状态 | 全部通过，当前 SLA 余量充足（E2E P90 最大 0.3s vs 门限 0.4s） |
| 4DP SLA 合规状态 | **全部不达标**，E2E P90 超出 SLA 门限 4~8 倍 |
| 高 QPS 延迟下降现象 | 4TP 独有，4DP 不存在 |
| 根本原因 | 8K token 长前缀 prefill 是该模型的决定性瓶颈，TP 并行计算是唯一有效的加速路径 |

### 5.2 部署建议

**强烈推荐使用 4TP×1实例**，主要理由：
1. 当前 4TP 在 4~7 QPS 全程满足 SLA，且有约 25% 延迟余量（0.3s vs 0.4s 门限）
2. SGLang 前缀缓存在 4TP 单实例上效果显著（高 QPS 时延迟可降至 0.1s）
3. 4DP 方案的延迟倒退无法通过调参修复，根源是单 GPU 算力不足以在 400ms 内完成 8K token prefill

### 5.3 后续建议

#### 建议 A：扩大 4TP 测试范围，找真实拐点
- 当前 QPS=7.0 时延迟还在下降，真实拐点可能在更高 QPS（15~25 req/s 区间）
- 建议将测试范围扩展至 7.0 → 20.0 req/s

#### 建议 B：若需更高吞吐，考虑 4TP×N 多实例横向扩展
- 4TP 单实例在达到真实拐点后，可通过增加 4TP 实例数（2实例、3实例）线性扩容
- 这比 4DP 的路径更优：每实例仍保持 4TP 张量并行的低延迟优势
