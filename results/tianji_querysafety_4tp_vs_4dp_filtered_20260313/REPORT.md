## 1. 测试背景

### 对比目的

相同 GPU 总量（4 卡 H100）下，比较两种部署策略：

| 部署方式 | 描述 | GPU 使用方式 |
|---------|------|-------------|
| **4TP×1实例** | 4 GPU 张量并行，单实例 | 4 GPU 协同处理每条请求 |
| **1TP×4DP** | 1 GPU 单实例 × 4 副本（数据并行）| 每条请求由 1 GPU 独立处理 |

### 模型特征

| 项目 | 值 |
|------|----|
| 模型 | `tianji_query_safety/v2p3_ep1`（4B 安全检测） |
| System Prompt | ~8K Token（固定大模板 + 大量 few-shot） |
| User Input | 极短（几十 Token） |
| 最大输出 | 256 Token（短 JSON 结构化输出） |
| 部署框架 | SGLang（开启 KV Cache 前缀匹配） |

### 剔除说明

| 剔除档位 | 所属组 | 理由 |
|---------|--------|------|
| `opti_qps_6.79` | 1TP×4DP | 业务层面异常点，延迟表现与邻近档位不一致 |
| `opti_qps_7.00` | 1TP×4DP | 同上，成功率 99.99% 且延迟异常，不代表稳态表现 |

两个档位原始请求均完整、无 POST 异常或流解析错误，属于测试过程中偶发的非稳态数据。

### SLA 基准

| 指标 | 门限 | 说明 |
|------|------|------|
| **E2E P95** | **≤ 400ms** | 主判断指标（快进快出模型） |
| E2E P90 | ≤ 400ms | 辅助判断 |
| TTFS P90 | ≤ 1,500ms | 通用基准 |
| 请求成功率 | ≥ 99% | 稳定性基准 |

## 4. 分析

### 4.1 结论不变：4DP 全档不达标，根本原因是单 GPU prefill 算力不足

剔除两个异常档位后，4DP 的整体表现趋势**无任何变化**——全部 28 档 E2E P90 均在 1.5s ～ 2.5s 范围内，超出 SLA 门限（400ms）4~8 倍。这进一步证明异常点的存在不影响整体结论：

> **1TP×4DP 方案根本无法满足该模型的延迟 SLA**，瓶颈在于单 GPU 必须独立处理 8K Token 的 prefill，计算时间远超 400ms 门限。

### 4.2 两组性能对比

| 指标 | 4TP×1实例（最差档） | 1TP×4DP（典型档） | SLA 门限 | 倍差 |
|------|----------------|-----------------|---------|------|
| E2E P90 | 0.294s | 1.5~2.5s | 0.400s | **5~8x** |
| E2E P95 | ~0.35s | 1.8~3.5s | 0.400s | **5~10x** |
| TTFS P90 | 0.289s | 1.5~2.5s | 1.500s | — |

### 4.3 4DP 延迟波动说明

4DP 在 28 档之间延迟波动较大（1.467s ～ 2.511s），没有随 QPS 升高而单调递增的规律，原因：

- 每个 DP 副本实际承载约 1.0~1.75 req/s，负载较轻，队列等待不是主要因素
- 主要瓶颈是**单 GPU prefill 计算时间**，随 GPU 调度和内存带宽状态波动
- 各档位延迟的随机性来自 GPU 上下文切换、内存压力等系统级因素，而非流量本身

## 5. 结论与建议

| 维度 | 结论 |
|------|------|
| **整体判断** | **4TP 完胜 4DP，4DP 方案不可用于生产** |

| 异常档剔除影响 | **无影响**，剔除前后结论完全一致 |
